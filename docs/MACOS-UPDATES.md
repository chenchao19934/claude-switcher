# macOS 界面更新

新版「版本更新」页使用正式 Release 的预编译 App，可更新界面、核心脚本及 STUN 探针。旧版只有检查和复制命令按钮，需先替换一次新版引导 App 或使用安装器；之后可直接在页面更新。

## 更新来源与安装包

客户端只读取维护仓库 `chenchao19934/claude-switcher` 的 `releases/latest`，接受非草稿、非预发布且标签为 `v主版本.次版本.修订版本` 的正式版本。它按本机 arm64 或 x86_64 架构选择 `ClaudeSwitcher-<版本>-macos-<架构>-update.zip`，同时下载同一 Release 的 `SHA256SUMS-release.txt`。没有正式发布版本时显示「仓库尚无正式发布版本」，不会回退 main 源码或在用户电脑编译。

外部清单必须包含目标 ZIP 的 SHA256，资产 URL 必须属于同一仓库、同一标签和准确文件名；缺项、重复项、不安全路径或校验失败均中止。ZIP 根目录包含：

- CI 预编译的 `Claude切换器.app`，包括 `Contents/Resources/desktop-update.py`。
- `core/claude-switch.sh`、`core/stun-probe.py`、`core/desktop-update.py`。
- `daemons/claude-bodyguard.sh`、`daemons/tz-watchdog.sh`、`daemons/bodyguard-settings.py` 三份系统组件模板，仅用于校验和只读比对。
- `SHA256SUMS` 内部清单，精确覆盖上述核心三工件和守护三模板；`VERSION` 必须与 Release 版本一致。

界面更新还验证 App 标识、版本、可执行架构、内置更新组件和签名。ZIP 不允许路径越界、符号链接或重复文件。界面按正式语义版本识别新版，单独修改界面也必须递增并发布版本；同版本文件异常不作为可静默覆盖的新版。

日常更新需要 Python 3，无需 Xcode 命令行工具。首次安装器／源码安装仍在本机编译 App，需要编译工具，不应与后续 Release 更新混淆。App、核心、探针及其父目录必须属于当前用户、可写、无符号链接且位于同一磁盘；root 实际更新会被拒绝，旧 root 更新服务需通过安装器迁移为用户态 LaunchAgent。正式团队签名或包含 Widget 的 App 需使用相同签名的专用更新渠道，当前通用更新流程会拒绝替换。

## 页面操作与事务

1. 页面始终显示 App 自身的当前版本。点击「重新检查」只读取 GitHub Release 元数据，展示最新正式版本；检查中、获取失败和尚未发布分别显示。此时不下载更新包，不写账号、客户端日志、更新锁或安装文件。
2. 发现新版后，点击「更新并重启」并确认。更新器持有共享锁，校验并暂存 CI 已编译的 App，按原赋值行保留五个代理／地区配置，检查脚本语法并执行完整 14 项安全审计。硬项必须全部 `ok`，只有既有六项可选检查允许按设置警告或跳过；缺行、重复、非零退出或安全失败均中止。
3. 准备完成后，独立用户态 worker 接管事务，确认旧 App 退出后再备份替换 App、核心和探针。App 内置更新器随 App 一起升级。替换后再运行完整审计，新版 App 必须返回一次性启动确认；替换、复审或启动确认失败时回滚，并尝试重新打开旧版。

暂存和备份位于 App 同目录的 `.claude-switcher-update-<事务编号>/`，权限为当前用户私有。worker 在接管和写入前核对事务记录及工件，重复 apply、暂存变化或原安装变化均拒绝继续。成功后保留 `previous-app.app`、`previous-core.sh` 和原有探针对应的 `previous-stun.py`，以及不含 IP／凭据的事务结果；失败时保留仍有恢复价值的备份。确认完整成功前，不要删除备份或不明暂存目录。

终端 `update`／`update --auto` 使用同一正式 Release 包，仅替换核心、探针及用户态更新组件，分别保留 `.bak`，自检失败则回滚三者；它不替换 GUI，也不写 GUI 版本标记。`update-check` 与 `update --check` 为只读检查。页面更新按 Release 的语义版本更新 GUI，终端核心检查则同时比对核心和配套脚本内容。

界面更新与终端／12 小时核心自动更新共用 `~/.claude-switcher/.update.lock`，已有锁时拒绝并发，不自动删除不明锁。可处理的异常或中断会释放自身锁；强制断电、不可捕获终止或磁盘故障可能需要结合事务记录手动恢复。不要在未确认备份和运行进程的情况下清理锁或暂存。

账号数据与存档、检查设置、代理配置以及 root 所有的保镖、时区看门狗和周期配置组件不参与替换。准备及替换后的安全审计沿用正常 `checkdetail` 行为，会更新已有最近检查记录；它们不启动 Claude。系统组件模板有差异时只提示另行运行安装器，不在用户态更新中提权部署。

下载优先使用已配置的代理环境变量；仅有 HTTP 代理时用于 HTTPS CONNECT，没有环境代理时读取 macOS 已启用的系统 HTTP(S) 代理。下载限制 HTTPS、响应大小和超时；错误只显示 HTTP／TLS／超时等分类，不打印代理地址、IP 或凭据。不要关闭 TLS 或跳过任一层 SHA256 校验。

## 维护者发布流程

1. 确定尚未发布的三段语义版本，例如 `1.2.3`。仅 GUI 变化也应递增版本；已有版本不覆盖、不重新上传资产。
2. 检查源码、文档和根目录 `SHA256SUMS` 已同步。获得当次明确授权后，才创建并推送 `v1.2.3` 标签；普通 main 提交推送授权不包含打标签和发布。
3. 标签触发 GitHub Actions，也可在 Actions 对已有正式标签手动重跑；默认分支及同名版本分支不能发布。流程在同一标签上复用现有检查门，通过适用隔离／平台测试后，分别在 arm64 与 x86_64 macOS runner 编译 App、校验版本和架构并生成更新包。
4. 两个架构都成功后，汇总安装包及其他平台资产，生成统一的 `SHA256SUMS-release.txt`，一次性创建正式 Release。已有 Release 不覆写；失败应先定位原因，不能跳过检查或校验。

Fork 的 Actions 可能需要维护者先在 GitHub 仓库页面启用。该流程描述发布机制，不表示首个正式 Release 已创建、Actions 已启用或当前版本已完成真实安装态更新验收。打标签、发布 Release、运行安装器和部署维护者本机仍须当次明确授权。

仓库回归使用临时 HOME、假 Release 网络与假 App 进程，覆盖校验、代理、事务、重启确认和回滚。CI 首次正式运行、实际下载与真实 App 替换仍需单独验收，隔离测试和编译成功不能替代这些验证。
